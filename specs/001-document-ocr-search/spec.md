# Feature Specification: Document OCR, Ingestion & Semantic Search

**Feature Branch**: `001-document-ocr-search`  
**Created**: 2026-08-07  
**Status**: Draft  
**Input**: User description: "Build a angular app in frontend and backend app. We need to make application where the user can upload document and there will be OCR that take the content of the pdf and then need to make filter the text come from it as pre-peration for embedding content and chunking..."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Upload, Extract & Structure Document (Priority: P1)

A user uploads a PDF document. The system extracts text via OCR, filters and cleans the extracted content, chunks it, and then uses an LLM to structure the data into a predefined regulation/action schema. The user reviews the raw extracted text and the structured result side by side, and confirms to save.

**Why this priority**: This is the core ingestion pipeline. Without structured data in the database, searching and querying cannot happen. Everything downstream depends on this flow.

**Independent Test**: Can be fully tested by uploading a sample PDF, reviewing the extracted text and structured JSON, and confirming the save. Delivers a populated database with structured document data.

**Acceptance Scenarios**:

1. **Given** a valid PDF file, **When** the user uploads it, **Then** the system extracts all text content and displays it to the user in a readable format.
2. **Given** extracted text from a PDF, **When** the system processes it, **Then** the text is filtered/cleaned and split into manageable chunks using recursive chunking.
3. **Given** text chunks from a document, **When** the LLM structures them, **Then** the output conforms to the regulation/actions schema (regulation name, types, actions with penalty/additions details).
4. **Given** the user sees both raw text and structured JSON, **When** they click confirm, **Then** the PDF file is stored, each chunk is embedded and saved in the vector database, and the structured data is persisted.
5. **Given** the user disagrees with the structured output, **When** they edit the plain text and trigger re-structuring, **Then** the LLM re-generates the structured JSON based on the updated text.
6. **Given** the user disagrees with the structured output, **When** they directly edit the structured JSON, **Then** the edited JSON is used for the final save.
7. **Given** the user wants to abandon the upload, **When** they click cancel, **Then** the process is discarded and they return to the upload screen.
8. **Given** an invalid or corrupted PDF, **When** the user uploads it, **Then** the system displays a clear error message without crashing.
9. **Given** a PDF with no extractable text (image-only without readable content), **When** extraction runs, **Then** the system informs the user that no text was found.

---

### User Story 2 - Semantic Search & Chat (Priority: P2)

A user types a natural language question about the ingested documents. The system embeds the query, finds the most semantically similar chunks using a vector search function, and returns a context-aware answer generated by the LLM using a predefined system prompt.

**Why this priority**: This is the value-delivery layer — users need to query the ingested regulations to get answers. It depends on P1 but is independently testable once documents exist.

**Independent Test**: Can be fully tested by submitting a query against pre-existing embedded documents and receiving a contextually relevant answer.

**Acceptance Scenarios**:

1. **Given** ingested documents exist in the system, **When** the user submits a natural language question, **Then** the system returns a relevant answer based on the document content within a reasonable time.
2. **Given** a user query, **When** no document chunks meet the similarity threshold, **Then** the system responds that no relevant information was found rather than hallucinating an answer.
3. **Given** a user query, **When** the LLM generates an answer, **Then** the response references information only from the provided document context.
4. **Given** the system prompt is configured, **When** answering user queries, **Then** the LLM follows the instructions in the system prompt (language, tone, format).

---

### User Story 3 - Document Management (List, Download, Delete) (Priority: P3)

A user can browse all previously uploaded documents, download their original PDF files, and delete documents (along with their associated embeddings and structured data).

**Why this priority**: Document lifecycle management is important for maintaining a clean dataset, but the core ingest and search flows provide value even with manual cleanup.

**Independent Test**: Can be fully tested by viewing the document list, downloading a specific PDF, and deleting a document — verifying that the document, its chunks, embeddings, and structured data are all removed.

**Acceptance Scenarios**:

1. **Given** documents have been uploaded, **When** the user views the documents list, **Then** all previously saved documents are displayed with their names and upload dates.
2. **Given** a document exists, **When** the user clicks download, **Then** the original PDF file is downloaded to their device.
3. **Given** a document exists, **When** the user deletes it, **Then** the PDF, all associated embedding chunks, and structured data are permanently removed from the system.
4. **Given** a document is deleted, **When** a user searches for content that was only in that document, **Then** no results from the deleted document are returned.

---

### Edge Cases

- What happens when a PDF exceeds the maximum allowed file size?
- How does the system handle PDFs with mixed languages (Arabic + English)?
- What happens if the LLM fails to structure the data (timeout, malformed JSON)? The system displays an error message with a Retry button, allowing the user to re-attempt the structuring call without re-uploading the document.
- How does the system handle duplicate uploads of the same document? The system detects same-filename uploads and warns the user, requiring explicit confirmation before proceeding.
- What happens when the vector database connection is unavailable during save or search?
- How does the system handle very short documents (single page with minimal text)?
- What happens when a user deletes a document while a search query is in progress?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST accept PDF file uploads from users through a web interface.
- **FR-002**: System MUST extract text content from uploaded PDFs — attempting direct text extraction first, then falling back to OCR for image-based PDFs where no text layer exists.
- **FR-003**: System MUST filter and clean extracted text to prepare it for embedding (removing noise, artifacts, formatting issues).
- **FR-004**: System MUST split cleaned text into chunks using recursive character-based chunking with configurable chunk size and overlap via environment variables.
- **FR-005**: System MUST send chunks to an LLM to structure the content into a predefined schema (regulation with types and actions, supporting Arabic and English fields).
- **FR-006**: System MUST display the raw extracted text and the LLM-structured JSON in a tabbed interface for review. The user must be able to: (a) edit the plain text to re-trigger automatic re-structuring, (b) edit the structured JSON directly, or (c) cancel the process entirely.
- **FR-007**: System MUST, upon user confirmation, store the original PDF, generate embeddings for each chunk, and persist the structured data and embeddings in the vector database.
- **FR-008**: System MUST provide a semantic search endpoint that accepts a natural language query, embeds it, and finds the top matching chunks via a vector similarity function with a configurable similarity threshold.
- **FR-009**: System MUST send matching chunks as context to an LLM with a configurable system prompt, returning a context-grounded answer to the user.
- **FR-010**: System MUST list all previously uploaded documents with their names and upload dates.
- **FR-011**: System MUST allow users to download the original PDF of any previously uploaded document.
- **FR-012**: System MUST allow users to delete a document and cascade-delete all associated embeddings, chunks, and structured data.
- **FR-013**: All AI provider configuration (base URL, API key, model, embedding model) MUST be configurable through environment variables only, allowing provider swaps without code changes.
- **FR-014**: System MUST respond gracefully when no chunks exceed the similarity threshold, informing the user that no relevant content was found.
- **FR-015**: System MUST set a configurable timeout on LLM calls. When an LLM call fails (timeout, malformed JSON, or schema mismatch), the system MUST display an error with a Retry button.

### Key Entities

- **Document**: Represents an uploaded PDF file. Has an identifier, original filename, upload timestamp, and the stored PDF file itself.
- **DocumentChunk**: A segment of extracted and cleaned text from a document. Has content, an embedding vector, a reference to its parent Document, and metadata (chunk index, page information).
- **StructuredRegulation**: The LLM-structured output representing a regulation extracted from the document. Contains name (Arabic/English), description (Arabic/English), and associated regulation types.
- **RegulationType**: A category within a regulation (e.g., "Attendance Regulation", "Leave Regulation"). Contains name (Arabic/English) and references its parent StructuredRegulation.
- **RegulationAction**: A specific action within a regulation type (e.g., "Unexcused Delay", "Sick Leave"). Contains action name (Arabic/English), action type (Penalty/Addition), value type, and the actual value (text, decimal, days, percentage).
- **SearchQuery**: Represents a user's semantic search interaction, including the raw query, the generated embedding, matched chunks, and the LLM-generated response.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Users can upload a PDF, view extracted text and structured data, and confirm save in under 60 seconds for a typical 20-page document.
- **SC-002**: Semantic search queries return context-grounded answers within 10 seconds.
- **SC-003**: 100% of document deletions cascade correctly — no orphaned embeddings or chunks remain after a document is removed.
- **SC-004**: The system processes documents containing both Arabic and English text without data loss.
- **SC-005**: Users can switch AI providers by changing only environment variables — no code changes required.
- **SC-006**: The system never returns hallucinated answers when no relevant document content exists; instead it clearly states no information was found.

## Clarifications

### Session 2026-08-07

- Q: Where should structured regulation data be stored vs embeddings? → A: Everything in Supabase (relational tables for regulations/types/actions, vector table for chunks/embeddings, storage for PDFs). Neon Postgres is not used.
- Q: What can user do when they disagree with LLM-structured output? → A: Three options: (1) edit the plain extracted text and re-trigger structuring automatically, (2) edit the structured JSON directly, or (3) cancel and restart with a different document upload.
- Q: What happens on duplicate document upload? → A: Allow duplicates with a warning — user must confirm before proceeding.
- Q: What happens when LLM structuring call fails (timeout, malformed JSON, schema mismatch)? → A: Show an error immediately with a "Retry" button for the user to re-attempt the structuring call.
- Q: Should the system handle text-based PDFs, image-based PDFs, or both? → A: Both — try direct text extraction first; fall back to OCR only if no text is found (image-based PDF).

## Assumptions

- Users are technical enough to review structured JSON output and confirm or reject the LLM's interpretation.
- PDF documents are primarily text-based regulations with Arabic and English content; the extraction pipeline attempts direct text extraction and falls back to OCR for image-only pages. Handwriting OCR is not required.
- All data is stored in Supabase: relational tables for structured regulations/types/actions, a vector-enabled table for chunks/embeddings, and Supabase Storage for PDF files. pgvector extension and the match RPC function are pre-configured.
- The LLM provider supports both chat completions and embedding generation.
- No authentication or multi-user isolation is needed — this is a single-user demo/POC.
- File uploads are limited to 50MB per PDF (configurable via environment variable).
- The system prompt for the chat LLM is defined in environment variables.
- The structured output schema (regulation types/actions) is fixed for the POC; no dynamic schema editing is required.
- Chunk size and overlap are defined in environment variables with sensible defaults (e.g., 1000 characters, 200 overlap).
